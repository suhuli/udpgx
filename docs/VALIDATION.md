# v0.1.0 验证记录

日期：2026-10-13。
环境：Linux 开发工作区；Go 1.27.2；.NET SDK 8.0.425；目标 Windows x64 / .NET Desktop Runtime 8.0.31。

## 已完成

- Go 网络核心编译为 Windows x64 GUI 子系统 EXE。
- WPF 客户端/提供端共享界面编译、发布为 Windows x64 自包含应用。
- `go test -race -count=1 -timeout 120s ./...` 通过；`go vet ./...` 通过。
- 配置持久化、默认 STUN 首项、非法端口、重复监听、拒绝 TURN 的自动检查。
- 控制帧编码/解码和超长帧拒绝。
- 本地 STUN 测试服务器响应产生 srflx 候选，无 relay 候选。
- 一个提供端、三个客户端真实建立 ICE + QUIC 连接，跨独立本地 socket 完成 TCP 转发。
- 三个客户端共 12 个并发 HTTP 二进制回显请求，每个载荷 512 KiB，结果逐字节一致。
- 三个客户端 TCP 上传半关闭后仍完整收到服务端响应。
- 客户端重启、提供端重启后重新建立链路，并继续完成传输。
- 关闭测试 Redis 后，界面状态来源报告信令不可用，而已有 P2P 连接仍能转发新的 HTTP 请求。
- 流量计数更新，关闭引擎释放资源；上述测试启用 race detector。

原始包级结果在 `test-results.txt`。测试在本机网络/本地临时 Redis、STUN、HTTP、TCP 服务间进行。没有连接用户 Redis，没有使用用户凭据，也没有查询预置公共 STUN 的实时状态。

## 尚未验证，不作成功保证

- 真正 Win10 机器上的 WPF 显示、托盘、缩放、首次运行提示。
- Windows Named Pipe 实机通信与权限、Windows 服务安装/自动启动/卸载、UAC、防火墙规则操作。
- 四个用户指定公共 STUN 的当前可达性、实际端口与服务稳定性。
- 双端真实跨运营商 NAT 打洞、IPv6、防火墙组合与系统休眠恢复。
- 真正 RDP 登录、长时间桌面画面体验和 Windows 登录/注销场景。
- 真实性能基准、极端丢包、高带宽长延迟网络和长时间稳定性。

因此交付称为“首版”，不称为经过生产验证的产品。成功的本机测试不等于能穿透所有 NAT。

## Windows 首次验收建议

1. 两台 Win10 x64 完整解压；先不开启自动启动或系统服务，验证普通模式。
2. 配置相同 Redis / DB / 连接组，先检查信令状态和在线发现。
3. 提供端本机先访问目标网站，确认目标确实可用。
4. 客户端添加网站映射、保存，查看候选数量、是否取得 STUN 映射、实际直连状态。
5. 访问映射并观察连接数/流量；随后验证 RDP。
6. 验证托盘恢复、停止释放端口、退出结束核心；再考虑安装无人值守服务。
7. 如失败，导出两端运行日志并说明网络类型。不要发送含密码的配置文件。
